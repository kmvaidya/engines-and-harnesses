the idea underneath

Every AI interaction is a contract

“The map, a representation of the work to be done, is my prompts and skills and context, it's what I give Claude. The territory is where the work needs to happen, the codebase, the real world, its actual constraints. […] The difference between the map and the territory is what I call unknowns.” Thariq Shihipar, Anthropic · “A field guide to Claude Fable 5: Finding your unknowns” · July 2026

Every task you hand over starts with a gap between what you said and what's true. The contract is how both sides close it.

Thariq Shihipar is a member of Anthropic's technical staff; this is from his field guide on the Claude blog. His metaphor is map and territory. The prompt is never the whole picture. The question is how much of the gap you close before the model starts guessing.

The grid isn't only about you. The model brings its own knowns and gaps, and the dangerous cases are where your unknown knowns meet its unknown unknowns: the rule you'd never think to say, which it has no way to know. That's where confident wrong answers come from.
what the harness is for

A harness shrinks the guesswork

QuadrantWhat you can doIn the harness
Known knownsWrite them down onceInstructions, AGENTS.md
Known unknownsInvestigate before acting/init, a blind-spot pass, plan before code

Unknown unknownsLimit the damage and catch it earlyHooks, review, verification

The contract between you and the model lives in the harness. Written once, reviewed like code, used by everyone who opens the repo.

This is the thesis. Every piece we build today lands in one of these rows. "Blind-spot pass" is Thariq's term: ask the model to find your unknown unknowns before you start. Example prompt: "I'm about to change X and know nothing about this module. Do a blind-spot pass and tell me what I should be asking." The goal isn't zero risk. It's fewer pitfalls and faster work.

          anatomy

          A harness has three parts

          Prompt

          What it's told: built-in instructions, your instruction files, skills, and your message.

          Memory

          What it carries between sessions: notes it saved, and facts it learned about the repo.

          Tools

          What it can do: read, search, edit, run commands, reach other systems. Hooks check each use.

          Everything in the recap table belongs to one of these three. Instructions, AGENTS.md and skills are prompt. Memory files and Copilot Memory are memory. Terminal, file edits, MCP, and the hooks that police them are tools.

          guardrails first

          Instructions ask. Hooks enforce.

          An instruction

          “Never run git push.” The model will usually comply.

          A hook

          A script that runs before every tool call and can deny it. The model doesn't get a vote.

          “Adding a rule to an instructions file is not equivalent to enforcing that rule with a hook.” VS Code docs, agent customization

          Hook points in VS Code: SessionStart · UserPromptSubmit · PreToolUse · PostToolUse · PreCompact · SubagentStart · SubagentStop · Stop

          Hooks are the first thing I set up on any repo I don't own. Their first job is safety. We'll see other uses at the end of this section. Hooks in VS Code are still in Preview; in the Copilot SDK they're GA.
          hook one

          The agent never pushes

          /create-hook Deny the agent from running git push in any form. Give the model a reason so it asks me to push instead.
          .github/hooks/guardrails.json
          {
  "version": 1,
  "hooks": {
    "preToolUse": [
      { "type": "command", "cwd": ".github/hooks",
        "command": "node block-git-push.cjs",
        "timeoutSec": 10 }
    ]
  }
}
          .github/hooks/block-git-push.cjs
          let raw = '';
process.stdin.on('data', c => (raw += c));
process.stdin.on('end', () => {
  const ev = JSON.parse(raw);
  let args = ev.tool_input ?? ev.toolArgs ?? {};
  if (typeof args === 'string') {
    try { args = JSON.parse(args); } catch {}
  }
  const cmd = String(args.command ?? '');
  if (/\bgit\b[^\n;&|]*\bpush\b/i.test(cmd)) {
    process.stderr.write(
      'Policy: the agent may not run git push. ' +
      'Ask the user to push.');
    process.exit(2);          // 2 = deny
  }
});
          Run /create-hook live and talk while it works; good moment for questions. Compare what it generates with this reference version. This one works in both Local and Copilot sessions: exit code 2 blocks in both, and it reads both payload shapes. The full tested version (which also writes the JSON decision) is in research/round3-hooks-context-memory.md Q4. Needs Node on the machine. Test it once: ask the agent to push, and watch it get refused. Note: in the Copilot harness a crashing hook blocks every tool call, so test before committing it.

          Two layers on purpose. The instruction stops the model from trying in the first place, which saves noise. The hook catches it when it tries anyway.           know the limits

          What a hook can't see

          • A command that reaches the file without naming it: a wildcard, a variable, a script
          • A workspace search whose results include lines from the file
          • Files you open or attach yourself. They never pass through a tool call
          • A hook that crashes or times out in a Local session lets the call through

          For a hard guarantee, admins can set managed Read(...) deny rules. Hooks are a guardrail, not a wall.

          Worth being honest with a bank audience. Content exclusions, the admin feature for keeping files away from Copilot, still don't apply in VS Code agent mode. Managed deny rules apply to Copilot-harness sessions for users who receive enterprise managed settings.
          beyond safety

          Hooks do more than block

          Hook pointUse it to
          PostToolUseFormat, lint, type-check or run the affected tests after every edit, and hand the results back to the model
          SessionStartAdd context at the start: “the onboarding guide is 40 commits out of date”
          StopRefuse to finish until the tests pass
          PreToolUseRewrite a command before it runs, or ask you first
          Not a hook masterclass, just the menu. Example: after any Python edit, run mypy and the matching pytest file, and feed failures back so the agent fixes them before it says it's done. Stop hooks cost extra turns, so guard against loops.

          turn history into rules

          Let the Git history teach it the conventions

          Read the last 200 commits with git log. Describe our conventions for branch names, commit messages and PR titles, with three real examples of each. Then draft a "Git" section for .github/copilot-instructions.md. Mark anything you're unsure of.

          You don't have to know a team's conventions to write them down. The history already does.

          Tribal knowledge that leaves a trail. The AI drafts it, the team corrects it, and it goes in the file. The same trick works for code style: "look at the last 20 merged PRs and describe what reviewers keep asking for".
          writing rules

          Write what it can't infer

          Instead ofWrite
          Follow best practices for errors.Return Result from service methods. Don't throw across service boundaries.
          Run the tests.Run ./gradlew test. Integration tests need a database, so skip them and say so.
          Don't touch generated code.Files in src/generated/ come from api/*.yaml. Edit the YAML and run make codegen.
          NEVER use System.out!!!Log through AuditLogger, because audit logs feed compliance reports.
          “Include the reasoning behind rules.” · “Focus on non-obvious rules.” VS Code docs, custom instructions
          Specific, checkable, with a reason, and with the alternative. The reason lets it handle the case you didn't list. Shouting doesn't help: newer models take emphatic language too literally (Anthropic's prompting docs now advise plain wording). Examples are made up for a generic repo.
          a rule I use everywhere

          Build for how long it will live

          instructions
          ## How to approach a change
- First decide whether this is a one-off (a script, an investigation,
  a migration) or something that will live in the codebase.
- If it will live on, build it properly: follow the existing
  structure, add tests, and leave no workaround for someone else
  to clean up.
- If you can't tell which it is, ask.

          Left alone, an agent optimises for finishing the task in front of it.

          Personal recommendation, from experience: AI wants to get to "done" as fast as possible, which produces patchwork that someone has to rework into proper practice later. This rule makes it stop and classify the work first. It can go in the team file or in your personal one.
          two files, two audiences

          copilot-instructions.md or AGENTS.md?

          .github/copilot-instructions.mdAGENTS.md
          Who reads itCopilot: chat, cloud agent, code review, CLICopilot and most other AI coding tools
          GitHub's rule of thumb“Copilot, always know this for this repository”“Any agent, always know this”
          Per folderNo. Use *.instructions.md with applyToYes. The nearest file takes precedence

          When both exist, both are loaded. Keep them from contradicting each other.

          AGENTS.md is an open, cross-tool format (stewarded under the Linux Foundation), not Copilot's version of CLAUDE.md. Copilot also reads CLAUDE.md. A practical split: project facts any tool needs go in AGENTS.md; Copilot-specific behaviour goes in copilot-instructions.md. VS Code: "Applicable instruction sources are additive. Do not depend on a file order or precedence rule to resolve conflicts."
          the habit that matters most

          When it gets something wrong, fix the harness

          1. Notice the mistake
          2. Correct the output
          3. Ask why it happened: what didn't it know?
          4. Add one line to the harness, so no session repeats it

          Fixing the output helps you once. Fixing the harness helps everyone, every time after.

          This is how unknown knowns get captured. If you know the fix, write the fix. If you only know it's wrong, write what to avoid and why. You can ask the agent itself: "Add a line to copilot-instructions.md so this doesn't happen again", then review the line.

          the skill

          /update-onboarding-doc

          .github/skills/update-onboarding-doc/SKILL.md
          ---
name: update-onboarding-doc
description: Updates ONBOARDING.md to match recent repository changes. Use when
  asked to refresh the onboarding guide, or after new setup steps, renamed
  commands, or new environment variables.
---
1. List recent changes: `git log --since="14 days ago" --name-status --no-merges`.
   Focus on build files, setup scripts, CI workflows and top-level docs.
2. Read ONBOARDING.md.
3. Update only what a new joiner would hit: new prerequisites, renamed
   commands, new variables, removed steps. Keep the headings and tone.
4. Edit only ONBOARDING.md.
5. Reply with one line per edit and the commit that caused it.
          The name must match the folder name, lowercase with hyphens, or the skill silently fails to load. The description decides when Copilot picks it up on its own, so write it like a search query. You can also generate one: /create-skill and describe it.
          nobody remembers to run it

          Let a hook notice when it's stale

          .github/hooks/onboarding-staleness.cjs
          const { execSync } = require('node:child_process');
const git = cmd => {
  try { return execSync(`git ${cmd}`, { encoding: 'utf8',
          stdio: ['ignore', 'pipe', 'ignore'] }).trim(); }
  catch { return ''; }
};
const last = git('log -1 --format=%H -- ONBOARDING.md');
const behind = last
  ? Number(git(`rev-list --count ${last}..HEAD`)) : 0;
if (behind > 30) {
  const note = `ONBOARDING.md is ${behind} commits behind. ` +
               'Suggest running /update-onboarding-doc.';
  process.stdout.write(JSON.stringify({
    additionalContext: note,
    hookSpecificOutput: { hookEventName: 'SessionStart',
                          additionalContext: note } }));
}

          Registered under sessionStart, it runs once at the start of each session.

          When the guide falls behind, the agent starts the session knowing it.

          SessionStart can add context in both Local and Copilot sessions. The script was tested on a repo 31 commits behind, an empty repo and a non-repo folder; it stays silent on any git error. Register it in guardrails.json next to the others: "sessionStart": [{ "type": "command", "cwd": ".github/hooks", "command": "node onboarding-staleness.cjs" }].

          Narrow agents beat broad ones

          broad

          “Find the problems in this codebase.”

          Different every run. Mostly style comments.

          narrow

          “Find tests that can never fail: no assertions, skipped, or mocking the thing under test.”

          Repeatable. Each finding is checkable.

          The more precisely you specify the job, the more consistent the result.

          one job each

          Seven auditors

          AuditorLooks for
          Code qualityDuplication, long functions, dead code, TODO and FIXME comments
          DesignGod classes, cyclic dependencies, layers calling past each other
          TestsUntested critical paths, skipped tests, tests with no assertions
          DocumentationSetup steps that no longer work, undocumented APIs, comments that contradict the code
          Build and dependenciesUnpinned or end-of-life packages, unused dependencies, fragile build steps
          SecurityHardcoded secrets, injection-prone string building, missing authorisation checks
          Error handlingSwallowed exceptions, unchecked nulls, leaked connections and files

          Categories adapted from the technical debt taxonomy of Alves et al. (2014, 2016), plus security.

          Every auditor is read-only, writes findings to its own file with file:line evidence, and lists anything outside its lane under "Handoffs" instead of chasing it. The full list of what each must not do is in research/round3-framing-taxonomy-changes.md §2.2. Ask the room which categories matter most for their code.

          A custom agent with one job

          .github/agents/test-auditor.agent.md
          ---
name: Test Auditor
description: Finds weak or missing tests. Reports only.
tools: ['read', 'search', 'edit']
---
Audit the tests in the requested scope. Report:
- critical paths with no tests
- skipped or disabled tests
- tests with no assertions
- tests that call real external services

Write findings only to docs/audit/tests.md, one per line:

Do not edit any other file. Do not fix anything.
